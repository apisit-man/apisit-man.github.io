01 · DECISION

Build a guided course with a truthful simulation contract.

The recommended first release combines parameter-controlled electronics models, a readable circuit, linked Arduino examples and short learning tasks. It can live entirely on GitHub Pages. This package supplies the research, implementation specification, original bilingual curriculum, tested model/code seeds, prompts, templates and deployment helpers. Antigravity still needs to generate the frontend and 3D scenes, integrate them, run application QA and deploy.

Three different deliverables must stay distinct. This completed package is the generation workflow. The generated website is the next build output. A working live GitHub URL is the deployment result. Neither the website nor a live deployment is claimed in this report.

A guided model is suitable for learning causal relationships because its supported inputs and outputs can be tested. It should not pretend that every arbitrary program, circuit or physical failure is supported. Make the model boundary visible in Thai and English and give learners concrete opportunities to compare the model with real measurements later.

02 · RESEARCH EVIDENCE

What the reference actually establishes

The live reference lists 16 lessons with a central 3D workspace, lesson tabs, code, serial output, settings and component navigation. Its language selector offers multiple languages but no Thai. The interface credits Dilum Sanjaya. [1]

Public delivered modules show Vite-style bundling and Three.js. The inspected run path starts predefined lesson models; compilation/upload messages are timed presentation effects, not an arbitrary C++ compiler in that path. Parameter settings also drive example text. These observations support a guided-model architecture, not a firmware-execution claim. [1]

The research browser could not create the WebGL scene. Tabs, pinout, code, settings and language navigation were inspected, but live scene gestures, audio and 3D visual quality were not verified. The delivered JavaScript was inspected read-only; no complete source or security audit was performed. [1]

Why the new implementation should separate simulation from rendering

The reference's visible failure mode makes an architectural improvement useful: when rendering is unavailable, learning should continue. Put electronics state and the simulation clock in independent modules. Both renderers subscribe to those modules. The circuit view must support controls, outputs, explanations and code, so the fallback is a full learning route rather than an error screen. This also helps schools with older GPUs, restricted browsers or remote desktops.

Research method and limits

Research combined the live application, its publicly delivered modules, official Google/GitHub/Arduino/Three.js documentation, component datasheets and established maker documentation. Source links and inspection hashes are supplied. No source repository or reuse license for the reference was established here; the implementation plan therefore uses newly written prose, code and procedural geometry. Public delivery of JavaScript is evidence about behavior, not permission to redistribute it.

Third-party showcase descriptions can lag a changing application. Prefer the current live catalog over older lesson counts. Similarly, a claim that a site was built with a particular AI model does not establish that another agent can reproduce it with one prompt, or that the result is technically correct. The workflow uses testable stages and observable acceptance gates instead.

AVR8js explicitly describes a CPU core that consumes precompiled machine code; external hardware behavior and its visualization must be added. It is not a drop-in Arduino C++ compiler or a complete circuit solver. [18]

Accuracy checks that shape the course

The target is Uno R3/ATmega328P rather than a generic board with assumed interchangeable features. Its digital pins, PWM-capable outputs and analog inputs establish the pin plan. The new button lesson uses INPUT_PULLUP to GND, so pressed is LOW. The code, diagram and reading must all reflect that convention. [7] [8]

The ADC/PWM lesson uses 0–1023 and 0–255 respectively, including integer mapping behavior. PWM is a duty-cycle command on the chosen board. The TMP36 lesson includes the 0.5V offset and 10mV/°C slope plus explicit ADC quantization; real sensor/reference uncertainty remains additional. [9] [10] [11]

The distance lesson uses the classic 5V Trig/Echo HC-SR04, not the Qwiic/I2C variant. A timeout is missing data. Force readings remain qualitative without calibration; motor speed is illustrative, and its drive path includes a driver and flyback protection. Step count is a configured assumption, not proof that a physical motor completed the commanded movement. [12] [13] [14] [15]

Resource lifecycle and interaction

Current Three.js WebGLRenderer requires WebGL2, and allocated graphics objects require explicit lifecycle management. Reuse the board and shared primitives; dispose replaced lesson resources and controls. Bound geometry counts, pixel ratio and logs. Keep a single simulation/render lifecycle and stop sound on Stop, lesson change or hidden document. [16] [17]

Every direct gesture needs a matching HTML control: button hold, knob angle, sensor fixture, servo command and piano keys. That gives keyboard/touch access and a way to test the same actions in both renderers. Handle pointer cancellation and blur so a press or note cannot become stuck. Reduced motion should change presentation, not the numerical model.

Learning sequence

Ask the learner to predict an output before changing a control. Change one variable and observe a reading, circuit indication and relevant code line. Invite an explanation and a boundary test. Record a lesson as explored through an explicit learner action; clicking Run alone should not imply mastery. Use teacher notes to discuss where a physical circuit could differ from the idealized model.

Thai and English as first-class interfaces

Default to Thai. A valid link language overrides a saved preference; otherwise use the saved language, then Thai. Translate lesson text, controls, errors, accessible labels, component descriptions, logs and print. Keep technical identifiers unchanged. Do not introduce multiple path prefixes that depend on server routing. The proposed share format is index.html?lang=th#button.

The physical OLED example uses the default library's ASCII font; explain that limit instead of pretending it can render Thai. The browser OLED representation still uses the selected language. Use Thai-capable system typography, readable line spacing and normal wrapping. The author credit can use Dr. Apisit Thongchai's name; no institutional endorsement or logo is assumed.

05 · WORKFLOW

Build in stages with evidence at every gate

Ordinary prompt files are the primary interface in this package: they work without installing another personal skill or depending on a particular slash-command setup. Google currently documents Agent Skills and deprecates legacy workflows; a reusable skill can be created later from stages that have proved useful. [2] [3]

  1. Foundation. Verify the seed, create app/, install compatible exact versions and establish build/type interfaces.
  2. Content and domain. Integrate all 16 lessons; normalize parameters; expand netlists and test code/model agreement.
  3. Interface and language. Complete responsive navigation, Thai/English, routing, settings and guarded local storage.
  4. 3D and circuit view. Generate original component geometry, camera/picking and a working SVG fallback for every lesson.
  5. Experiments and teaching. Connect controls, clock, readouts, generated examples, sound, print, share and learning tasks.
  6. QA and repair. Test acceptance scenarios in production output, including mobile, missing WebGL, no echo and repeated scene changes.
  7. Release preparation. Audit dist/ and test nested hosting; inspect or document the actual site's publication route.
  8. Deployment. After local review, publish only the requested app subtree, verify Pages succeeded and test the returned live URL.

The master prompt runs stages 1–7 by default. START_HERE also includes an optional launch block authorizing deployment in the same run after all release gates pass. Separate review, deployment and resume prompts are provided. The agent must write a status file containing completed gates, actual commands/results, current failure and next action. A context limit or interruption should leave a usable checkpoint, not cause the next session to recreate the project from scratch.

Protect the current website

The deployment prompt first verifies the actual repository and whether Pages publishes from root, docs, a generated branch or an existing build pipeline. Adding an app-only Pages workflow to a whole-site repository can replace the published artifact with only the app. Therefore the default is subtree integration while preserving the current pipeline. The separate-repository workflow template is clearly marked for that alternative only. [5] [6]

The supplied staging helper is dry-run-first. It requires an explicit checkout and publish root, refuses symlinks/unknown target ownership and edited deployed files, copies only the built app, preserves the existing root page and does not commit or push. It retains stale owned assets rather than deleting a directory that might contain user work. Antigravity then reviews the diff and follows the existing publishing process.
